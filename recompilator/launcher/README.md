# RECOMPILATOR — the launcher

The brief (2026-09-06): one program, presented like an emulator, that lets you select a ROM,
recompile and build it, then play it. As simple to use as possible, in the spirit of ZSNES, with a
3D starfield instead of 2D snowfall.

`recompilator.exe` is the front door of the one program. It is **not a game tree** — no ROM, no
recompiled functions. It boots the *same* engine every game boots (SDL window →
`recomp::start(cfg)` with the same callbacks) and simply never calls `recomp::start_game()`, so the
window belongs to the launcher until the user picks something. A built game is a module
(`archive/<game>pc/module/<game>.dll`) loaded into this process against the host's exported C ABI
(`recomp_host_abi.txt`, generated by `tools/make_host_abi.ps1` from the built executable).

## Build

Standalone (the tree adds its own copy of the engine):

```
cmake -S recompilator/launcher -B recompilator/launcher/build/windows-x64 -G "Visual Studio 17 2022" -A x64
cmake --build recompilator/launcher/build/windows-x64 --config Release -- /m:2
```

Through the master build (the engine objects are built once and shared with every game tree):

```
cmake -S _masterbuild -B <builddir> -G "Visual Studio 17 2022" -A x64
cmake --build <builddir> --config Release --target recompilator -- /m:2
```

Either way the exe lands at **`recompilator/launcher/build/windows-x64/Release/recompilator.exe`**
(the target sets its own `RUNTIME_OUTPUT_DIRECTORY`). `/EHsc` must stay OFF (see the block at the
top of `CMakeLists.txt` and `_masterbuild`'s). After the engine's exports change, re-run
`tools/make_host_abi.ps1` and re-run CMake configure for a game tree: the ABI file is read at
configure time.

## The screens

The top bar is `ARCHIVE / VIDEO / AUDIO / CONTROLS`, and the selected tab is the screen.

| screen | what is on it |
|---|---|
| **ARCHIVE** | the 3D starfield; **ADD ROM** at the top; the user's games (the `archive/` folder next to the program, plus any recipe the user has built) with a state column: NOT BUILT, BUILT, TITLE, PLAYS |
| **ADD ROM** | the native file dialog → the cartridge's own header and hashes → *Recognised: <title>* or *New cartridge*; `Enter` builds it (from the recipe when one exists), `B` builds it blind from the cartridge alone |
| **BUILD** | the telemetry terminal: the real pipeline (`tools/build_entry.ps1`), one row per stage with its status, its measured seconds and the evidence line it ended on, and a progress bar of stages done out of stages total |
| **PLAY** | the game module runs in this window; `Esc` (or the pad's guide button) asks before leaving |
| **VIDEO** | RT64's live settings; `F1` in a game opens the renderer's own menu |
| **AUDIO / CONTROLS** | what is true: the device in use, the pad that was found |

Keys in the menus: `↑ ↓` select · `← →` tabs · `Enter` play or build · `A` add ROM · `B` build blind
(on the ADD ROM screen) · `Esc` back · `Q` quit. A pad works too: D-pad, A/Start = Enter, B = Esc,
Y = add ROM, X = build blind. Nothing needs the mouse.

In a game: keyboard arrows = D-pad, `W A S D` = control stick, `Z` = A, `X` = B, `Left Shift` = Z,
`Enter` = Start. Pad: D-pad, A, B, Start, bumpers = L/R, Back = Z, left stick = control stick,
right stick = C buttons.

## Where everything comes from

**Never per-game code in the host.** A row on the ARCHIVE is a directory holding an `entry.json`:
the ROM's hashes and entry point, the title and release date, the sweep verdict and whether it
reached gameplay (`sweep.reached`), and the list of files the entry carries. Entries the program
authors itself (a blind build) are marked `origin: blind` and `sweep: LOCAL`; a shipped recipe is
never written to by the program.
